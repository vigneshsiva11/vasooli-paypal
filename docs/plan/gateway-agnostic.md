# Gateway-Agnostic Pipeline Architecture & Amendments

This document defines the architectural amendments and design specifications for transitioning the Vasooli pipeline to a gateway-agnostic architecture supporting both Razorpay and PayPal, while keeping the existing Razorpay pathway strictly unregressed.

---

## Architectural Amendments (Recorded for Future Steps — Do Not Implement Yet)

### 1. Multi-Currency Rulebook Profiles (USD / INR)
* **Design**:
  * Establish a currency-keyed profile structure in `app/policy/rules.py` (or a dedicated configuration module).
  * **INR Profile**: Preserves existing thresholds and costs identically (`AUTO_AUTHORIZE_BELOW = 5000.0`, `NEVER_AUTO_AT_OR_ABOVE = 25000.0`, `MINIMUM_ERV = 25.0`, existing intervention costs in INR).
  * **USD Profile**: Introduces currency-tailored thresholds and costs scaled to USD economics (e.g. `AUTO_AUTHORIZE_BELOW = 60.0`, `NEVER_AUTO_AT_OR_ABOVE = 300.0`, `MINIMUM_ERV = 0.50`, and intervention costs in USD).
  * **Rulebook Fingerprint**: The rulebook fingerprint must hash the specific currency profile used for evaluation into the fingerprint (`rb1_<hash>`), ensuring full audit-trail integrity while leaving the existing INR fingerprint unchanged.

---

### 2. PayPal Decline Code Mapping & Diagnosis Fallback
* **Design**:
  * Limit the deterministic diagnosis lookup to:
    1. Codes observed directly in the spike:
       * `5120` (Insufficient funds / card declined) -> `insufficient_funds`
       * `00N7` (CVV / security code failure) -> mapped to customer-must-update cause (`payment_method_update_link` / `card_expired`)
       * `0500` (Generic decline / Do not honor) -> `issuer_declined`
    2. Codes verified against PayPal's official decline code reference table.
  * **Gemini Routing**: Any raw decline code, processor response, or text outside this ratified table falls through to the Gemini diagnosis model (`POST /diagnose/{event_id}`), maintaining strict accuracy boundaries without guessing.

---

### 3. Payment Advice Code Policy Guard (Retry Blocking)
* **Design**:
  * Implement a dedicated policy check utilizing `processor_response.payment_advice_code` provided in PayPal transaction failure webhooks/capture responses.
  * If the payment advice code indicates a hard refusal (e.g., card revoked, stopped recurring payment, fraud hold, or non-retryable advice code), policy blocks retry actions (`immediate_retry` / `delayed_retry`) with a clear policy verdict reason (e.g. `retry_blocked_by_payment_advice`).
  * Prevents costly non-viable retry attempts and protect merchant processing reputation.

---

### 4. Vault Token Collection (`customer_to_vault_token`)
* **Design**:
  * Maintain a dedicated MongoDB collection `customer_to_vault_token` mapping `customer_ref` to persistent vault payment tokens.
  * Ingest and update records automatically from `VAULT.PAYMENT-TOKEN.CREATED` webhook events delivered by PayPal.
  * Enables future autonomous re-attempts and automated charge executions on vaulted payment instruments without customer intervention.

---

### 5. Idempotent Pipeline Orchestrator with Simulated Clock
* **Design**:
  * Introduce an orchestrator to run the full pipeline sequence (`ingest -> diagnose -> decide -> authorize -> execute -> verify`) end-to-end idempotently.
  * Incorporate a pluggable / injectable clock (`now: datetime`) so that cooldowns, expiry intervals, and spaced re-evaluations can be deterministically tested and orchestrated without real-world latency or fragile sleeping.

---

### 6. Custom ID Convention (`cust:<ref>` vs `ev:<event_id>`)
* **Design**:
  * Enforce clear distinction in PayPal payload `custom_id` fields:
    * `cust:<ref>`: Applied to original merchant orders and initial checkout/charge requests, identifying the customer entity.
    * `ev:<event_id>`: Applied to recovery payment links and recovery orders generated by Vasooli, enabling direct reverse-lookup and correlation from incoming webhook payloads back to the specific `RevenueEvent`.

---

### 7. PayPal Outcome-Follows-Event Invariant for WebhookVerification (Step 4)
* **Design**:
  * In Step 1, the `_outcome_must_follow_the_event` validator on `WebhookVerification` was relaxed so that `razorpay_event` is optional for non-Razorpay webhooks (e.g., PayPal webhooks).
  * In Step 4 (Verification Port & Adapters), a strict PayPal outcome-follows-event invariant must be added for `WebhookVerification`:
    * When `gateway == "paypal"`, validate that the incoming PayPal webhook event name (e.g., `CHECKOUT.ORDER.COMPLETED`, `PAYMENT.CAPTURE.COMPLETED`, `INVOICING.INVOICE.PAID`, `INVOICING.INVOICE.CANCELLED`) strictly dictates `outcome` (`recovered`, `cancelled`, etc.) via a declared PayPal event-to-outcome mapping table.
    * Guarantees that neither gateway's verification record can freely choose its outcome or deviate from the signed event payload delivered by the respective gateway.

## Status of Models (Completed in Step 1)

1. **`RevenueEvent`**: Added `gateway` (`"razorpay"` | `"paypal"`, default `"razorpay"`) and `gateway_ref` (`Optional[str] = None`).
2. **`ExecutionRecord`**: Added `gateway`, `gateway_ref`, and `gateway_url`. Updated `_artifacts_must_match_the_action` validator so PayPal artifacts (`gateway_ref`, `gateway_url`) are accepted on completed link actions while Razorpay link artifact validation remains strictly identical.
3. **`WebhookVerification`**: Added `gateway` and `gateway_ref`. Made Razorpay-specific fields (`razorpay_event_id`, `razorpay_event`, `razorpay_payment_link_id`) optional.
4. **`assertion`**: Added to verification records (`"gateway_verified"` | `"merchant_asserted"`), defaulting for legacy documents from `source` (`webhook` -> `gateway_verified`, `manual_confirmation` -> `merchant_asserted`).
5. **Indexes & Literals**: VerificationSource literals left unchanged (`"webhook"`, `"manual_confirmation"`). No indexes modified yet.
